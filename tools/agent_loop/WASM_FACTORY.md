# The wasm factory — code and content generation in the browser

The world computer's missing half. The engine already runs `.zxapp`
manifests in the browser (`zxv_app.wasm`); the **factory** generates them
there too, so any user's device can produce and publish content to IPFS
with no server, no H100, and no network round trip. The lattice makes it
possible: because the checks are **computed** (deterministic integer
functions of a lattice point), generation needs no model — it needs the
lattice and the manifest grammar, both of which fit in a few hundred KB
of wasm.

## The two wasm modules

| Module | What it does | State |
|---|---|---|
| **`zxv_app.wasm`** | runs a `.zxapp` with the node's semantics (the pillars + the four tribute addresses) | ✅ built, 280 KB |
| **`zxv_factory.wasm`** | generates a `.zxapp` from a lattice point (the header, the entries, the computed checks) and packages it for IPFS | the new module |

The two share the same pillar runtimes and the same lattice code, so they
can ship as one module with two entry points (`zxw_load`, `zxw_generate`)
— smaller and consistent.

## The factory's entry points (the wasm ABI)

```
zxw_generate(app_index, out_ptr, out_cap) -> len
    writes the complete `.zxapp` for the app at that lattice index:
    the header, the `needs`, the `provides`, the logic slots and the
    checks COMPUTED from the lattice. Returns the byte length.

zxw_generate_check(app_index, entry_index, out_ptr, out_cap) -> len
    writes one entry's exact check line (the lattice-determined values).

zxw_pack(app_ptr, app_len, out_ptr, out_cap) -> len
    builds the IPFS-ready package: the manifest, its CID (the SHA3-256
    over the canonical bytes), and the CARv1 block for upload.

zxw_verify(bytes_ptr, len) -> status
    the same verification the node runs, in the browser: parse, load,
    check. 0 = passed.
```

Every pointer is into the wasm linear memory and bounds-checked, exactly
as `zxv_app_wasm.c` already does.

## Why the lattice makes browser generation possible

| Requirement | Without the lattice | With it |
|---|---|---|
| The checks | a model call (a server, a GPU, a network) | **an integer function** — microseconds, offline |
| The grammar | a model's judgment | **a fixed template** — the header, the provides, the slots |
| The values | drafted, then judged | **computed**, so they are correct by construction |
| The size | a model runtime (GBs) | **the lattice + the grammar** (a few hundred KB) |
| The network | a round trip to a builder | **none** — the device is the builder |

That is the world computer: the generation is deterministic, so it runs
wherever the wasm runs — a phone, a laptop, a low-power device — and the
result is **identical** on every surface (the same lattice point, the
same computed checks, the same bytes).

## The upload path (fully functional on publish)

```
1. the user picks a lattice point (their app index / their space)
2. zxv_factory.wasm generates the complete .zxapp (the checks computed)
3. zxv_app.wasm verifies it locally (the node's own verdict, in the browser)
4. zxv_pack builds the CARv1 block and computes the CID
5. the block uploads to IPFS (Filebase) — content-addressed, verifiable
6. the CID is the app's permanent address: anyone can fetch and run it
```

Because step 2 is deterministic and step 3 is the node's own verification,
**the upload is trustworthy by construction**: the content's CID commits
to bytes that already passed the checks, and any peer can re-verify from
the CID alone.

## What the H100 must build and test

1. **The factory entry points** in a new `web/boot/zxv_factory_wasm.c`,
   sharing the lattice code with the app engine.
2. **The lattice code in C** — port `mk_lattice_apps.py`'s point
   generator, projection and check computation to freestanding C11 (exact
   integers, no allocation), so the wasm carries it.
3. **The packing** — the canonical bytes, the SHA3-256 CID, the CARv1
   block (the same format the curriculum CAR uses).
4. **The three spaces in the browser**:
   - *positive*: generate an app, verify it, the checks pass;
   - *negative*: a tampered byte fails verification and the CID changes;
   - *neutral*: the boundary indices (0, 8, 144) generate deterministically.
5. **The cross-surface equivalence**: the browser-generated bytes are
   **byte-identical** to the node-generated bytes for the same index —
   the strongest proof that the factory is the same system everywhere.

## The honest boundary

The factory generates the **structure and the checks** deterministically;
the app's human-readable **logic body** (the prose the entry computes) is
still authored — but it is the only part that needs authoring, because
everything else is computed. That is the honest shape: the lattice
removes the model from the answers and from the grammar, and leaves it
only the body, which a user (or an agent, or the H100) can supply — and
the body is verified locally before upload.

So: **the browser becomes a full node of the factory** — generate,
verify, pack, publish — and the world computer's users produce content
for the network from their own devices, offline-capable, with no server
in the loop.
