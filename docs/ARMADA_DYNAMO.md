# The nine-armada dynamo — why "only inbound rules are allowed" is the mechanism

Measured from the Contabo API (2026-10-18), not remembered.

## The constraint

`POST /v1/firewalls` refuses anything but inbound rules:

```
{"statusCode":400,"message":"Bad Request only inbound rules are allowed!"}
```

The validator's own shape, read off its errors:

```
name    string, <= 255
status  "active" | "inactive"
rules[] each carrying an "inbound" array whose entries are
        protocol  "tcp" | "udp" | "icmp"
        action    "accept" | "drop"
        status    "active" | "inactive"
```

An empty `rules` array returns HTTP 500, so at least one inbound rule is
required. **The last structural detail of the `rules` array is still open**
— every complete shape tried returns the same "only inbound" refusal, so the
discriminator the validator wants sits somewhere other than the nested
`inbound` key. Next probe: create with one minimal inbound entry and read the
validator's own next field name, or add rules to an existing firewall by PUT.

## The principle: the Möbius dynamo

A firewall that admits only inbound traffic looks like a limitation. It is
the opposite. **Each node's outbound packet is another node's inbound
packet**, so the mesh needs exactly ONE inbound rule per node — accept the
VNA on `8724/udp` — and nothing else:

```
        one trigger packet
              |
   IND --inbound--> EU --inbound--> JPN --inbound--> US-c
    ^                                                |
    |                                                v
   SIN <--inbound-- US-w <--inbound-- US-e <--inbound-- UK
              (AUS joins the ring)
```

Every arrow is an inbound rule on the receiving node, and every arrow is
generated by the sending node's own response. One packet in, and the ring
sustains itself: **the traffic is the mechanism, not the thing being
permitted.** That is the dynamo — the same principle Walter Russell draws in
the optical dynamo generator, where a single impulse sets a closed loop
turning because the loop's own motion is what feeds it.

## What that means for SCP-144

The Vinea sessions are already outbound-initiated (`vna_host_start` dials the
nine baked peers on 8724), and the SCP-144 lattice binding rides inside the
handshake. So the armada needs:

1. **One inbound rule per node**: `udp 8724 accept` — the VNA.
2. **The door's rule** for the browser/HTTP face: `tcp 80 accept` (and 443).
3. **The shell's rule**, only when the operator wants it: `tcp 22 accept`.

With those three, the ring closes on itself and the telemetry rides the
ladder (`telemetry.zxapp`, F1..F12 = 1..144) with no further permission —
because no node ever needs to be permitted to *speak*, only to *be heard*.
