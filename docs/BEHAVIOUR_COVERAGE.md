# Behaviour coverage

Which checks in this tree assert behaviour and which only assert presence. Started from an
outside review (2026-10-15) whose main recommendation was to expand the mutation and
property tests and make banner-style checks assert behaviour rather than presence. This page
is the inventory, what changed, and what is left. Findings outside test coverage are in
[AUDIT_FINDINGS_2026-10-15.md](AUDIT_FINDINGS_2026-10-15.md); mutation scores in detail are in
[tests/MUTATION_REPORT.md](../tests/MUTATION_REPORT.md). Line coverage is a different measure
and lives in [COVERAGE.md](COVERAGE.md).

## Classes

- **BEHAVIOUR**: the check computes something and compares it with an expected value that a
  wrong implementation would not produce (a published test vector, a hand-worked result, a
  reference model).
- **PARTIAL**: the check runs real code but compares it only with itself (two sides agree, a
  round trip closes) or tests part of the result.
- **PRESENCE**: the line or check passes whenever the code is linked or the call returns,
  whatever it computed.
- **On failure**: `halt` stops the boot; `fail-line` prints `[FAIL]` or `[??]`; `fail-line (CI
  fails)` is a fail line that the CI boot check now treats as a failure; `none` cannot fail.

### What changed

1. **CI now fails on a boot self-check that fails** (arm64, x86_64). Those kernels print
   `[FAIL]` and boot on; the CI boot check used to look only for `[BOOT_OK]`, `[AI_OK]` and
   fault markers, so every behavioural boot line on them was, to CI, presence only.
   `ZXV_BOOT_DENY_FAIL=1` (`build_system/ci_boot_check.sh`) adds `[FAIL]` and `[??]` to the
   fault markers. Both healthy boots print neither (checked under QEMU); with one RFC 7748
   byte changed the arm64 boot check fails. riscv and arm32 already halt with `[BOOT_FAIL]`.
2. **Boot checks that compare known answers**: X25519 against RFC 7748 section 6.1, IPFS
   against all 32 bytes of SHA-256("abc"), the event-space audit prints its real verdict, and
   an ML-KEM disagreement is a `[FAIL]`, not a `[WARNING]`.
3. **Property tests for the engineered core**, each against a reference model written in the
   test, run by `make -C kernel verify-all` through `tests/harness/tiers.py props` (plain,
   ASan+UBSan, and Q32.32 where the module has that path):

   | Module | Test | What the reference model checks |
   |---|---|---|
   | module binding | `kernel/src/modbind/test_modbind.c` | power-factor table, registry refusals, 1,500 random port graphs and capability graphs against a reference fixpoint (resolve, withdraw, restore, carrier), hold reasons, compose algebra; the boot gate itself through a linked declaration table: healthy, failing, unprovided, cycle, contract clash, duplicate, zero drive, and the power readout of a phased graph worked by hand |
   | Z[phi] | `kernel/src/e8/test_zphi.c` | 400,000 random operands against 128-bit arithmetic, every overflow guard at its edge, phi^k = F(k-1) + F(k) phi to k = 90 |
   | swarm economy | `kernel/src/swarm/test_swarm_props.c` | budget R1-R5 against a largest-remainder reference, market M1-M8, random worlds checking conservation and no minting after every step, settlement against a reference, ledger entries and witnesses, reserve audit against every tampered field |
   | lpres | `tests/host/test_lpres_props.c` | full four-valued tables (chain order, not Belnap), algebraic laws, registry against a reference, name and digest edges |
   | oseq | `tests/host/test_oseq_props.c` | random DAGs against a bitset transitive closure, commit and reject, cycles, replay window, exact boundaries, a DAG wider than the old traversal stack |
   | nine capitals | `kernel/src/zcapital/test_zcapital_props.c` | 200,000 random exchanges against the rule order and conservation, the offer/seek book against a reference simulation |
   | HKDF / TLS 1.3 | `kernel/src/tls/test_hkdf_props.c` | HMAC, Extract, Expand, labels and the whole schedule against Python's hmac/hashlib (`gen_hkdf_ref.py`), every length and buffer bound |

4. **Mutation targets** for those modules, nine of them in the CI subset at their measured
   scores (`tests/harness/mutator/targets.json`):

   Two bugs came out of it (oseq; AUDIT_FINDINGS F6, F7), both fixed.

### What is left

- **The `verify_banners.sh` checks stay presence checks.** They count symbols with `nm` to
  prove nothing was dropped by `--gc-sections`, which is a real question with a presence
  answer. Their behaviour counterpart is the boot line for the same subsystem, enforced on
  arm64 and x86_64 by item 1.
- **Announcement lines.** Most PRESENCE boot lines are `[INITIALIZED]`, `[REGISTERED]` or
  `[DRIVER ONLINE]` after an init call whose result is discarded. They do not claim a test,
  but they read like one. Gating each on its init's return value is mechanical and is listed
  in the audit findings rather than done here.
- **Declaration gate on arm64/x86_64** is advisory by stated policy (audit B1); its `[FAIL]`
  lines now fail CI.
- **riscv and arm32** keep the default boot check; their fail lines halt the boot already.

Reproduce: `python3 tests/harness/tiers.py props` (tests),
`python3 tests/harness/mutator/mutate.py --config tests/harness/mutator/targets.json --only lpres,oseq --phase both` (scores),
`ZXV_BOOT_DENY_FAIL=1 build_system/ci_boot_check.sh arm64 build_system/Makefile.arm64 30 "[AI_OK]"` (boot).
